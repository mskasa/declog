# Move pre-commit hook logic into Go binary (kizami hook pre-commit)

- Date: 2026-05-20
- Status: Active
- Author: masahiro.kasatani

## Context

The original pre-commit hook was a standalone shell script (`internal/initializer/templates/pre-commit`) that checked whether any file under `docs/decisions/` was staged alongside non-Markdown changes. If not, it printed a reminder to create an ADR.

This approach had three limitations:

1. **Config-unaware**: The script hardcoded `docs/decisions/` and could not respect `kizami.toml` settings (e.g. multiple document directories, custom paths).
2. **No Related Files check**: The hook could only suggest creating a *new* document. It could not detect when staged files were already referenced by an *existing* document whose content may need updating.
3. **Windows incompatible**: A shell script does not run on Windows without WSL or Git Bash, despite kizami claiming cross-platform support.

## Decision

Move all pre-commit hook logic into a Go command: `kizami hook pre-commit`.

The shell script template becomes a thin, portable wrapper:

```sh
#!/bin/sh
if command -v kizami >/dev/null 2>&1; then
  kizami hook pre-commit
fi
```

The Go command performs two checks:

1. **Related Files check**: Scans Active documents in all configured document directories. If any staged file matches a Related Files entry in a document that is itself not staged, a reminder is printed to review or update that document.
2. **New document check**: If no document is staged and non-Markdown files are present, a reminder is printed to consider creating a new document. This is the same behavior as the previous shell script, but now config-aware.

Both checks are soft reminders. The command always exits 0 and never blocks a commit.

## Consequences

- Pre-commit behavior is now config-aware: respects `audit.dirs` / `documents.dirs` from `kizami.toml`.
- Related Files check enables proactive reminders when existing decisions may need updating — not just when a new one should be created.
- Windows users get the same hook behavior as Unix users.
- The hook no longer works if kizami is uninstalled after `kizami init`. This is an acceptable trade-off: the hook was generated by kizami and assumes kizami is present. Silently skipping when `kizami` is not found avoids breaking commits.

## Alternatives Considered

**Enhance the shell script**: Possible with `grep` and path manipulation, but the script cannot read `kizami.toml`, making config awareness impractical without re-implementing a TOML parser in shell.

**Separate binary (kizami-hook)**: Would avoid the `command -v kizami` dependency, but adds distribution complexity. A subcommand on the existing binary is sufficient.
