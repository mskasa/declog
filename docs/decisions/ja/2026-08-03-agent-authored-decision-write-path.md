# `kizami_record_decision`：ゲート付き・新規ファイル限定の書き込みツール

- Date: 2026-08-03
- Type: ADR
- Status: Active
- Author: masahiro.kasatani

## Context

Agent Context LayerのStep 4（[[agent-context-layer-design]]）は、本ロードマップフェーズの書き込み側にあたる：`kizami_record_decision`。エージェントが判断を下した直後、まだ文脈を完全に持っている瞬間に決定を記録できるようにするMCPツールであり、そうしなければ人間が後で行うはずの文脈スイッチのコストがかかり、実際には多くの場合単に書かれずに終わってしまうタイミングである。これはStep 1〜3（すべて読み取り専用）とはリスクの性質が根本的に異なる：本フェーズで初めてリポジトリに書き込むツールであり、その安全性設計は読み取り専用ツール群のADRから継承するのではなく、明確に決定する必要がある。

## Decision

**既定でオフ、明示的なオプトイン。** `kizami mcp` は `--allow-write` を付けて起動した場合のみ `kizami_record_decision` を登録する。フラグがなければ、そのツールはエージェントの視点からは存在しない——登録はされているが拒否するのではなく、本当に存在しない。呼びたくなる対象も、回避すべきエラー経路もない。

**新規ファイル限定。** 本ツールは設定済みのdecisionsまたはdesignディレクトリ配下に、正確に1つの新規ファイルを作成し、他には何も触れない——既存ドキュメントの編集なし、ステータス更新なし、削除なし。具体的には、**`supersedes` 入力を持たない**：`cmd/log.go` の `--supersedes` フラグ（`kizami adr` が使用）は、新規ドキュメント作成後に*古い*ドキュメントのStatus行も変更する。これはまさに本ツールが行ってはならない副作用的な書き込みそのものである。古い決定をsupersedeすべきとエージェントが判断した場合でも、人間（または将来の、別途ゲートされたツール）が `kizami status <old> superseded --by <new>` を実行する必要がある。

**常に `Status: Draft`。** `decision.CreateFromDraft`／`CreateDesignFromDraft` を再利用し、これらは既に `template.RenderHeader` 経由でDraftを既定としている。Draftの決定はまだ何も縛らない（`internal/context` の `governs()` はDraftを除外する——[[related-files-single-definition]] 参照）。したがって、人間がレビューしてActiveに昇格させるまで、エージェント自身の将来の作業を黙って制約し始めることはない。またPRの差分にも載るため、ADR Update Policyの「コードと同様にレビューされる」という運用がそのまま適用される。

**両方の文書種別を、1つのツールで。** 入力は `kind` フィールド（既定 `"adr"`、または `"design"`）と、その種別に対応するセクションのフィールドを取る。ドラフト本文は、`internal/ai` の既存のAIドラフトプロンプトが既に使っているのと同じセクション順で構築する（ADRなら `## Context`／`## Decision`／`## Consequences`／`## Alternatives Considered`、設計文書なら `## Overview`／`## Background`／`## Goals / Non-Goals`／`## Design`／`## Implementation Plan`／`## Open Questions`）。Related Filesは両方で必須、それ以外は各種別の最低限（ADRなら `context`＋`decision`、設計文書なら `overview`＋`background`＋`design`）を超えて任意とする。

**エージェントからのパス制御は不可。** 本ツールが受け取るのはタイトルとセクション内容のみであり、出力先ディレクトリは常にサーバーの設定済み `decisions`／`design` ディレクトリ（`kizami.toml` から、サーバー起動時に解決される。他のすべてのコマンドと同一）である。ファイル名やディレクトリの入力は存在しないため、パストラバーサルの攻撃面もない。

## Consequences

- 当初の問題分析で特定された最大の梃子——決定が書かれないのは、書くことがコストの高い文脈スイッチを意味するから——に直接対応する。まさにその判断を下したエージェントが、同じ呼吸の中でそれを記録でき、追加コストはほぼゼロになる。
- エージェントが記述した決定はすべて、それに伴うコード変更と全く同じようにレビューされる差分中のDraftとなる。何かを縛るようになるのは、その後だけである。
- 古い決定のsupersede化は、本ツールによる1つのアトミックなエージェントの操作ではなく、依然として2段階の、人間が関与するプロセス（本ツールによる新規ドラフト、その後別途の `kizami status` 実行）のままである——これは本ツールの影響範囲に対する意図的な上限であり、見落としではない。
- `--allow-write` は設定ファイルの項目ではなく、実行ごとのフラグである。書き込みを有効にして `kizami mcp` を起動することは、誰かがオフにするのを忘れて永続化された既定値ではなく、毎回意識的に選ぶセッションごとの判断である。

## Alternatives Considered

**`kizami adr --supersedes` に合わせて `supersedes` も許可する**
輪をさらに閉じられる（エージェントが古い決定を自分で完全に退役させられる）が、本ADRの新規ファイル限定ルールがまさに避けようとしている「エージェントが触れると言っていなかったファイルをツールが編集する」というリスクを再導入してしまう。2段階の手動プロセスは、影響範囲を意味のある形で抑えるための小さな継続コストである。

**Draftステータスが既に実効果をゲートしているのだから、`--allow-write` を既定でオンにする**
Draftステータスは決定が*縛る*ことを防ぐが、ツールは呼ばれた瞬間に無条件でディスクにファイルを書き込む。エージェントが意図した以上の頻度で呼んでしまう（例：バグによる繰り返し呼び出し）可能性や、MCPサーバーがリポジトリに書き込むとユーザーが想定していない文脈で呼ばれる可能性は残る。明示的なフラグにより、「このセッションは自分のリポジトリに書き込んでよい」という判断を、オフにすることを知っておかねばならない既定値ではなく、人間が下す判断のままにできる。

**種別ごとに1つのツール（`kizami_record_adr`、`kizami_record_design`）にする**
ツールごとのスキーマはやや単純になるが、書き込みツールの定義数が倍になる。ADRと設計文書の違いは、どの見出しが適用されるかだけであり、エージェントが選ぶべき2つのツールより、1つのツールの1つのフィールドとしてモデル化する方が適切である。
