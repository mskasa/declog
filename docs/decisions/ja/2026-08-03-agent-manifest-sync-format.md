# `kizami agents sync` のエージェント向けマニフェスト形式と同期戦略

- Date: 2026-08-03
- Type: ADR
- Status: Active
- Author: masahiro.kasatani

## Context

Agent Context LayerのStep 2（[[agent-context-layer-design]]）では、エージェントがセッション開始時に既に読んでいるファイル（`CLAUDE.md`・`AGENTS.md`）に「パス→決定」のポインタ表を書き込む必要がある。これにより、エージェントが自分で探しに行かなくても決定が提示される。設計ドキュメントではここまでは決めているが、いくつか具体的な選択が残っている：ブロックをどう区切り、繰り返し実行してもべき等にするか。表の粒度と、決定の要約を1行に保つ方法。デフォルトでどのファイルを対象にするか。`--check` がどうCIビルドを失敗させるか。これらは外部から見える（生成されたMarkdownを読む人、あるいはそれをパースするスクリプトから見える）選択であり、後から変更すると破壊的変更になるため、実装時に場当たり的に決めるのではなく、ここに記録する。

## Decision

**区切られた、べき等なブロック。** 生成されるコンテンツはHTMLコメントのマーカーで囲む。

```
<!-- kizami:start -->
...
<!-- kizami:end -->
```

`kizami agents sync` は、既存のマーカー対が見つかればその間のコンテンツをそのまま置き換える。対象ファイルにマーカー対が存在しない場合は、ファイル末尾にブロックを追記する（推測した位置に挿入することは決してしない——位置を推測すると、その周囲の手書きコンテンツを壊すリスクがある）。これによりコマンドはべき等になり、pre-commitフックやCIステップから繰り返し実行しても安全である。

マーカーの検出は、単純な部分文字列検索ではなく、マーカー文字列がその行を単独で占めている（その行に他に何もない）ことを要求する。これは本機能を kizami 自身の `CLAUDE.md` にドッグフーディングした際に、実際に踏んだ問題から判明した：本ADRのDecisionセクション自体が例示として `<!-- kizami:start -->`／`<!-- kizami:end -->` を引用しており、本ADRが同期されると、その例示テキストがマニフェストのテーブル行の中に行の途中で埋め込まれることになる。単純な部分文字列検索では、そのデコイ（おとり）出現をブロックの終端と誤認識し、取得範囲を途中で切り詰めてしまい、`sync` の直後に `sync --check` を実行すると自分自身の書いた結果と矛盾するという事態が起きた。マーカーがその行を単独で占める（改行またはファイルの開始／終了で区切られる）ことを要求すれば、決定の本文中にマーカーらしきテキストが出現しても影響を受けない。

**Related Filesエントリ単位ではなく、決定単位で1行。** Active または Superseded の各決定（Supersededな決定を保持する理由は [[agent-context-layer-design]] を参照）は、テーブルにちょうど1行を持つ。そのRelated Filesエントリは1つのセルにまとめる（バックティックで囲み、カンマ区切り）。これはStep 1で確立したトークン予算の方針と一致する——マニフェストの存在意義は、安価で常時ロードされるポインタであることであり、ADR本文の第2のコピーになることではない。

**決定の要約セルは約160文字・単一行に強制的に切り詰める。** 要約は `kizami context` と同じ `## Decision`/`## Overview` 抽出を再利用する（全文ではない）。空白・改行はすべて単一のスペースに畳み込み、切り詰めた場合は末尾に `…` を付ける。160文字という長さは、`kizami context` の既定レスポンスで既に想定している1決定あたりのおおよそのトークン予算（設計ドキュメントのDesignセクション参照）と同程度に収める。そうしなければ、複数段落にわたる `## Decision` セクションが、本来「安価」であるはずのマニフェストを、セッション開始ごとに読み込むには高価なものにしてしまう。

**デフォルトの対象ファイル：存在する `CLAUDE.md` と `AGENTS.md`。** 両方存在すれば両方同期する。どちらも存在しない場合は作成しない（`kizami agents sync` はエラーを返し、先にどちらかを作成するよう案内する——ユーザーに代わってエージェント指示ファイルを勝手に発明することはしない。それはユーザーが決めることであり、kizamiが決めることではない）。異なるファイル名規約を使うプロジェクト向けに、`kizami.toml` の新設 `[agents]` セクション（`targets = [...]`）で設定可能にする。

**`--check` は、いずれかの対象のブロックが欠落または陳腐化していれば失敗（非ゼロ終了）する。** `kizami lint` のエラー／警告の終了コード規約に合わせる（エラーはビルドを失敗させる。マニフェストの陳腐化は、この一連のフェーズがまさに防ごうとしている失敗モードそのものであるため、警告ではなくエラーとして扱う）。

## Consequences

- マニフェストは決定論的に再生成・差分比較できるため、`--check` をCIゲートとして機能させられる。
- `CLAUDE.md`/`AGENTS.md` の他の手書きコンテンツには一切触れない——マーカーで囲まれたブロックのみを置き換える。
- 長く込み入った `## Decision` セクションを持つ決定も、ここでは必然的に1行のポインタに平坦化される。全文は `kizami show <slug>`（または `kizami context --full`）で1コマンド分の距離にある。これは意図的な非可逆圧縮であり、見落としではない。
- 変わったエージェントファイル命名を使うプロジェクトは `kizami.toml` に1行の設定を書けばよい。よくあるケース（リポジトリルートの CLAUDE.md および／または AGENTS.md）は設定不要である。
- 決定の要約はバイト数ではなくrune数で切り詰める——Goの文字列をバイトインデックスでスライスすると、マルチバイトのUTF-8文字（日本語など）を分断してしまう可能性がある（これも実装中に同様の経路で判明した：初期実装は本リポジトリ自身の `CLAUDE.md` に対して、日本語の決定要約を文字の途中で切ってしまい破損させていた）。

## Alternatives Considered

**末尾への追記ではなく、ファイル先頭付近にブロックを挿入する**
線形に読むエージェントにより早く決定を提示できるが、既存の任意のMarkdown内で安全な挿入位置を推測する必要があり、セクションを分断したり無関係なブロックの中に入り込むリスクがある。追記は曖昧さがない。ファイル内での並び順は、より早い位置に置きたいユーザー自身がマーカーを移動すればよい（移動後も、以降の同期は同じマーカー対をどこにあっても見つけて置き換える）。

**決定単位ではなく、Related Filesエントリ単位で1行にする**
「パスで直接grepできる」より密な表になるが、行数が決定あたりの平均エントリ数倍に増え、Step 1でまさに抑えようとしていたエントリ単位の冗長さを再導入してしまう。5つの関連ファイルを持つ決定は、同じ情報にマニフェスト上5倍のスペースを要することになる。

**要約セルに文字数上限を設けない**
実装は単純だが、1本の冗長なADRがマニフェスト全体のトークンコストを膨らませ、マニフェストが存在する理由そのもの（設計ドキュメント：「12件の決定にマッチした場合、エージェント本来のタスク文脈を圧迫してしまう」）を損なう。固定の上限を設けることで、個々のADRの書き方に関わらず最悪ケースを有界に保てる。
