# `kizami mcp` のツールを「動詞の写し」ではなく「問い」の形にする

- Date: 2026-08-03
- Type: ADR
- Status: Active
- Author: masahiro.kasatani

## Context

SDKの選定が決まった（[[use-official-mcp-go-sdk]]）ので、`kizami mcp` には具体的なツール定義が必要になる。最も素朴な案——`list`／`show`／`search`／`blame` をそれぞれ1つのMCPツールとして公開する——は、この一連のロードマップフェーズを動機づけた設計論議の中で、既に落とし穴として指摘されていた：エージェントはkizamiの動詞で考えない。「これから触るファイルを縛っているものは何か」「これは既に決定済みか」という問いで考える。動詞を写しただけのツール群は、対応する利益もなくエージェントが文脈に保持すべきツール定義の数を増やしてしまう——MCPのツールスキーマ自体がセッション開始時にトークンを消費するため、ツール数は無料ではない。

具体的なGo型を設計する過程で、さらに3点を詰める必要が判明した：既定でレスポンスに何を含めるか、1つのslugが複数の文書に解決される場合（本リポジトリで実際に起きている条件——`agent-context-layer-design` だけでも `docs/design/2026-08-03-agent-context-layer-design.md` とその `ja/` 版という2ファイルが既に存在する）をどう扱うか、searchが何を返すべきか。

## Decision

本ステップでは読み取り専用のツールを3つとする（書き込み可能な4本目のツールはStep 4に持ち越す——[[agent-context-layer-design]] 参照）。

**`kizami_decisions_for_files`** — 「これから読む・編集するファイルを縛っているものは何か」。`internal/context.Resolve` の薄いラッパー。入力：`{ paths: []string, full?: bool }`。出力：`kizami context --json` が既に生成しているのと同じ `context.Result` のJSON形状——1つのスキーマに、CLIとMCPという2つの入口。[[related-files-single-definition]] のマッチングと、設計ドキュメントのトークン予算方針（既定は要約のみ、`full` でエスカレーション）をそのまま再利用する。

**`kizami_search_decisions`** — 「これは既に決定済みか」。入力：`{ query: string, limit?: int, include_superseded?: bool }`。`kizami search`（すべての `.md` ファイルの全行をgrepし、kizami以外のMarkdownファイルも含めて生の行マッチを返す）とは異なり、このツールはまず `decision.List` で実際のkizamiドキュメントを列挙し、そのうえで各ドキュメントを大文字小文字を区別せずにチェックする。したがって結果は常に本物の決定であり、ドキュメント単位で1行になり、迷い込んだ `README.md` が出てくることはない。各結果は `slug`・`title`・`status`・`decision`（要約）・`path`・`superseded_by`・`excerpt`（最初にマッチした行——*なぜ*マッチしたかの文脈用）を持つ。Supersededな決定は既定で除外する（`include_superseded` で再度含められる）——「既に決定済みか」という問いには、ほとんどの場合現在の状態が欲しい答えであり、置き換えの経緯は要求時に取得できればよい。`limit` の既定値は10。

**`kizami_get_decision`** — 「全文をくれ」。入力：`{ slug: string }`。出力：`{ matches: [...] }`——単一の文書ではなく*配列*。slugは設定された文書ディレクトリ全体で一意であることが保証されていないためである。本リポジトリ自身のEN/JA ADRペアがまさにその実例だ：両言語版が同じslugを共有し、両方とも正当な文書である。

本ツールは意図的に `decision.FindBySlug`（`kizami show` を裏で支える関数）を再利用しない。`FindBySlug` はディレクトリツリー内で最初のマッチが見つかった時点で探索を打ち切る（`filepath.SkipAll`）——本ツールを実装する過程で判明したのだが、これは `kizami show <slug>` が今日、同じ設定済みディレクトリの配下にネストしたEN/JAペアのうちEN側しか返さない（両方は返さない）ことを意味する。`cmd.findAllBySlug` は設定済みの*トップレベル*ディレクトリをループして複数結果を期待しているにもかかわらず、である。`kizami_get_decision` は新設の `context.GetBySlug` に支えられており、これは認識された全ドキュメントを直接スキャンするため、両方を見つけられる。これは `kizami show` に既に存在する実在のギャップであり、本ADRが修正するものではない——リポジトリのオーナーが別途判断すべき事項として記録しておく。

ツールのレスポンスは、単一のJSON `TextContent` ブロック（テキストしかレンダリングしないクライアント向け）と、型付きの構造化コンテンツ（SDKの汎用 `AddTool[In, Out]` がGo構造体から出力スキーマを導出する仕組みを使う）の両方として返す——手書きで保守するJSON Schemaドキュメントは作らない。

本ステップに書き込み能力は含めない。ここで出荷する `kizami mcp` は `docs/decisions/`／`docs/design/` を読むだけである。`kizami_record_decision`（Step 4）は別の、明示的にオプトインするツールとして `--allow-write` の背後に置き、ここには含めない。

## Consequences

- ツール定義は3つ（4つ以上ではない）——動詞を写したツール群より1セッションあたりの文脈フットプリントが小さく、各ツールはエージェントが実際に持つ問いに答える。既に存在を知っているべきコマンドに答えるものではない。
- `kizami_get_decision` の呼び出し側は、よくある単一マッチの場合でも配列を扱う必要がある——小さなエルゴノミクス上のコストだが、言語バリアントを黙って誤選択したり、正当に曖昧なslugでエラーになったりすることが決してない、という見返りがある。
- `internal/context` には今、slugでドキュメントを探す方法が2つ存在する：新設の `GetBySlug`（全件スキャン、全マッチを見つける）と、既存の `decision.FindBySlug`（最初のマッチのみ、`kizami show`／`status`／`supersede` が使用）。両者は互換ではなく、ネストしたEN/JAペアに対する `kizami show` の現在の挙動は、単独でバグとして修正する価値があると言える——本ADRのスコープ外だが、別途の判断に値する。
- `kizami_search_decisions` のドキュメント優先の列挙は、非常に大規模なリポジトリでは生のgrepより遅い（grepエンジンがフラグを立てたファイルだけでなく、認識された全ドキュメントを開く）が、`internal/config` 自身のドキュメントコメントが既に本ツールの対象規模として想定している「数十〜数百ドキュメント」の範囲では有界である。
- 書き込みツールがまだ存在しないため、本ステップの `kizami mcp` には `--allow-write` フラグや書き込み安全性の設計は不要である。その関心事全体はStep 4に手を付けず持ち越す。

## Alternatives Considered

**CLIの動詞を1:1で写す（`list`・`show`・`search`・`blame`・`audit` を別々のツールにする）**
これは設計ドキュメントの初期分析がまさに警告していた失敗モードそのものである。CLIの動詞は、人間がコマンドを実行しようと決めたことを前提にしている。エージェントの実際のニーズは、同じリゾルバの上に載った、より小さい「問い」型のツール群で答えるべきであり、より大きい「動詞」型のツール群ではない。

**`kizami_get_decision` を、曖昧なslugでエラーにする（`kizami status`／`kizami supersede` のより厳密な `findBySlug` に合わせる）**
一部の既存コマンドとは整合するが、それらのコマンドがエラーにするのは、特定の1ファイルを*変更*しようとしていて、誤ったファイルを選ぶと破壊的になるからである。`kizami_get_decision` は読み取り専用であり、全マッチを返すことにコストはなく、エージェントが持たない追加文脈で再試行して回避しなければならないエラーより、厳密に有用である。

**モードパラメータを持つ単一の統合ツール `kizami_query` にする（3ツールの代わりに）**
ツール定義の数は減るが、3つの異なるレスポンス形状とセマンティクスを1つのスキーマの背後に押し込むことになる。汎用パラメータ設計は、名前が明確な3つの狭いツールより、モード文字列を持つ1つの過負荷なツールの方が、モデルが正しく使うのを難しくする傾向がある——MCPのツール選択品質は、一般に特定用途のツールから利益を得る。
